# PromptLab knowledge flow — validation updated 2026-10-19

## Current review

The current-source review covered the isolated workspace evaluation runner, verified-memory search, run-activity projection, and their immediate callers and shared helpers. The fifth live smoke exposed a Workspace Chat gap: selected-source retrieval could be skipped after a valid no-change decision. The sixth run then showed lexical retrieval could still return no evidence. A real PostgreSQL reproduction established why: the 312-character prompt and 197-character stored source were passed to `plainto_tsquery`, which requires all prompt terms to match. The worker now retries only explicit lexical retrieval with bounded task terms after the original query returns zero evidence.

- The runner launches Bubblewrap with isolated namespaces and drops capabilities. CPU, address-space, file-size, and open-file limits remain host-side. `RLIMIT_NPROC=256:256` is applied by the trusted, read-only mounted `prlimit` after Bubblewrap creates the user namespace. The sandbox test reads `/proc/self/limits` and confirms both process limits are 256; it also checks source/home visibility, inherited environment, network interfaces, independent snapshots, output limits, and timeouts.
- Verified memories come from the shared eligibility rebuild and runtime audience. The worker filters every memory source against the run's frozen document ID, version ID, version number, checksum, and permission before packing. The runtime projection exposes development inputs and development evidence only; the worker maps a bounded allowlist and does not pass model/effort controls, verifier criteria, holdout inputs, or case IDs to the optimizer.
- The worker returns up to five complete records under a 4,000 estimated-token aggregate budget. It estimates `ceil(UTF-8 bytes of serialized JSON / 4)`, not with a provider tokenizer. Task text is capped at 4,000 JavaScript string code units and candidate prompt text at 8,000 code units, with surrogate pairs kept intact. Oversized whole records are omitted while later records may still fit; omission or field clipping sets `truncated`. A matching result set with no complete record that fits returns `context_budget_exceeded`. This estimate applies to the memory result, not the user's prompt or other retrieval context.
- Monitoring projects only allowlisted search metadata: query character count, limit, result count, availability, approved reason codes, and truncation. It excludes the query, memory text, candidate prompt, and verifier data. The activity mapper now presents the verified-memory result count and clipping status.
- Workspace seeds one required memory search before optimizer egress and gates the existing single target call on its successful completion. The worker resolves a recommendation only for Auto effort; manually selected model and effort remain authoritative.
- When a Workspace run has selected source IDs but the optimizer did not complete source retrieval, the worker now calls the existing search handler with the original task before target preparation. It reuses retrieval already completed on the normal candidate path, builds target evidence through existing helpers, and revalidates the frozen source manifest. Empty selection stays empty, and explicit Graph retrieval remains strict. This closes the no-change retrieval omission without another optimizer call.
- For explicit lexical retrieval, the first query still uses the original task and selected IDs. Only a zero-evidence result enables a bounded task-term query, which requires two matching terms when available. The helper retains source caps and manifest freshness checks before and after retrieval; Auto routing and strict Graph behavior are unchanged. The [real-PostgreSQL regression](../../apps/worker/src/workspace-target-retrieval.integration.test.ts) checks retrieved quote, version, checksum, chunk, evidence ID, trace, manifest, isolation, stale/revoked changes, empty selection, and true no-match.
- The eighth-run planner query exposed a related empty-result state bug: the planner search and its task-terms attempt both returned zero, then a no-change recommendation left retrieval marked complete and target preparation skipped the unchanged user task. The completion rule now accepts useful planner evidence, or a full selected-source no-match only after the original task was searched. A zero-evidence planner result therefore reaches one bounded original-task fallback; empty user selection remains empty, selected IDs and frozen permissions stay scoped, and Graph remains strict. The new PostgreSQL replay returned zero for both retained planner queries and one exact source chunk for the original-task fallback.

Atlas is pinned to `wsl-fp-pbkk`; snapshot `20261018T121532-733d32b204cc` is stale. No matching curated notes were returned. No Atlas refresh or vault write was performed. This checkout has no Git metadata.
